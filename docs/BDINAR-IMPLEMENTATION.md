# BDINAR — تقرير التنفيذ والتحقق

نفذت التغييرات داخل المشروع القائم، دون إعادة بنائه أو نشر Production أو ربط أموال حقيقية. هذه نسخة تطوير بقاعدة بيانات ومصادقة حقيقيتين، وليست جاهزة للإطلاق التجاري. توجد متطلبات موسعة ما زالت غير مكتملة؛ تفاصيلها في القسم I.

## A. BEFORE — ما وجدته

- React + Vite + TypeScript + Wouter + TanStack Query، وخادم Express ضمن pnpm monorepo.
- Drizzle وpg مثبتان، لكن schema فارغة. بيانات السوق والطلبات والرسائل والمستحقات مصفوفات داخل `dinar-data.ts`.
- لا تسجيل أو جلسات حقيقية. هوية ثابتة باسم أحمد، واسم مختلف ثابت داخل Header.
- السلة المحلية موجودة، مع LIMITED/UNLIMITED وحجز المخزون وتجميع الطلبات حسب البائع. الحسابات بالفلس وعمولة البائع 10%، مع 18 اختبار نطاق قائم.
- الأسعار كلها KWD، دون أسواق أو فصل دولة الحساب عن سوق التصفح.
- بعض مسارات الطلبات والمحادثات والمستحقات لا تتحقق من الطرف الحالي، وDashboard يستخدم إحصاءات تجريبية.
- واجهات عروض وتفاصيل وسلة وطلبات وتعديل ونشر ومحادثة وإثبات تسليم ونزاع نصي. RTL وDark موجودان كأساس، دون Auth/Profile/Settings فعليين.
- التدقيق الأصلي: `docs/BDINAR-AUDIT.md`.
- النسخة الاحتياطية: `checkpoints/bdinar-before-auth-markets.tar.gz`، غير مضافة إلى Git. المرجع السابق: `4455e7cfb18ea92382cf578f3f308edfb53aceba`.

## B. DATABASE

استكملت Drizzle الموجود. PostgreSQL هو مصدر بيانات المسارات الفعلية، ولا يوجد fallback إلى ذاكرة مؤقتة عند غياب الاتصال.

الجداول الحالية 16:

| الجدول | الغرض والعلاقات |
|---|---|
| users | هوية واحدة للشراء والبيع، هاتف فريد مطبع، كلمة مرور مجزأة، دولة حساب وسوق نشط |
| sessions | تجزئة رمز الجلسة، FK للمستخدم، انتهاء صلاحية وفهارس للمستخدم والانتهاء |
| checkout_requests | مفتاح عدم تكرار لكل مستخدم، hash للمدخلات، ونسخة الاستجابة لإعادة المحاولة |
| markets | أسماء الدول والعملات، السعر بالأجزاء الصغرى، scale، وحالة النشاط |
| market_price_versions | أسعار سوق محلية مؤرخة بالأجزاء الصغرى مع فترة سريان |
| market_audit | سجل تغييرات الإدارة على حالة السوق والسعر وأهلية البائع |
| offers | FK للبائع والسوق، مخزون وحجوزات وحالة، بيانات المحتوى في JSONB |
| seller_market_eligibility | موافقة البائع لكل سوق عند اشتراط الأهلية |
| carts | FK للمستخدم والسوق، unique(user, market) |
| cart_items | FK للسلة والعرض، unique(cart, offer)، كمية صحيحة |
| orders | FK للمشتري والبائع والسوق، snapshot مالي، الحالة والبيانات الخاصة |
| order_items | FK للطلب والعرض، كمية وسعر وإجمالي محفوظ |
| conversations | محادثة واحدة لكل طلب |
| messages | FK للمحادثة والمرسل؛ المرسل null لرسائل النظام |

| seller_dues | مستحق واحد لكل طلب، مربوط بالبائع وعملة الطلب |

- جميع الجداول لها primary keys؛ للجداول timestamps المناسبة، بينما `checkout_requests` لديها `createdAt` فقط. أضيفت فهارس العرض حسب السوق والحالة والبائع، والطلبات حسب الأطراف والحالة وموعد انتهاء الحجز، والرسائل حسب المحادثة والزمن، والمستحقات حسب البائع والحالة.
- القيود تشمل الكميات الموجبة وصحة المخزون والمبالغ، واتساق الإجمالي مع الكمية والسعر.
- Triggers تمنع تغيير مالك/سوق العرض، وتغيير أطراف/قيم snapshot الطلب، وإدخال عنصر سلة من سوق آخر.
- سلسلة migrations الحالية من `0000` إلى `0005`؛ وتشمل `0000_faulty_firestar.sql` إنشاء الجداول والعلاقات والفهارس، و`0001_invariants.sql` قيود العمل، و`0002_cloudy_mach_iv.sql` مفاتيح Checkout وموعد انتهاء الحجز، ثم migrations توسعة الأسواق العالمية والتسعير والأهلية والتدقيق.
- تطبيق migrations ثم إعادة تشغيلها نجح دون إعادة إنشاء البيانات. فحص سجل migrations نجح.
- بقيت JSONB للمحتوى والوصف ونسخ عناصر العرض المتوافقة مع الواجهات الحالية؛ الهوية والملكية والأسعار والمخزون والعلاقات ليست معتمدة على حقول JSON مرسلة من المتصفح.

## C. AUTH

- تسجيل حقيقي من الخادم: الاسم، الدولة، رمز الهاتف، الرقم، كلمة المرور وتأكيدها، والموافقة على شروط نسخة الاختبار.
- تغيير دولة التسجيل يضبط رمز الاتصال؛ يمكن تصحيحه يدويًا.
- تطبيع الأرقام العربية والفارسية، المسافات وصفر الاتصال المحلي، والتحقق باستخدام بيانات أرقام الهواتف للدول الـ249 الموجودة في سجل ISO الحالي. ليس ضمانًا بأن الرقم مملوك أو قابل لاستقبال الرسائل.
- unique normalizedPhone يمنع التكرار حتى مع تزامن طلبات التسجيل.
- تجزئة `scrypt` بملح عشوائي، N=32768 وr=8 وp=1، ومقارنة timing-safe. لا تخزين لكلمة المرور نصيًا ولا إعادتها إلى العميل.
- `phoneVerified=false`؛ لا OTP وهمي ولا ادعاء تحقق.
- Cookie تحتوي رمزًا عشوائيًا 256-bit؛ المخزن في PostgreSQL تجزئة SHA-256 للرمز. HttpOnly، SameSite=Lax، Secure عند NODE_ENV=production. مدة الجلسة 7 أيام.
- `/auth/me`, `/auth/register`, `/auth/login`, `/auth/logout`، وحماية الواجهات وAPI.
- Logout يبطل الجلسة في PostgreSQL، ويمسح Cookie وTanStack Query cache، ثم يعيد التوجيه. اختُبر Back ثم محاولة إجراء محمي.

## D. MARKET

- `accountCountry` مستقل عن `activeMarketId`. تغيير السوق لا يغير دولة الحساب.
- discovery والتفاصيل تُعزل في الخادم بحسب سوق الجلسة. الزائر غير المسجل يبدأ في KW.
- تغيير `marketId` في query لا يتجاوز العزل. عروض البائع تبقى في السوق الذي نُشرت فيه.
- قائمة الأسواق تأتي من قاعدة البيانات، مع الأعلام والعملة وسعر الوحدة. نافذة اختيار ثم تأكيد عربي واضح.
- السلة مستقلة لكل مستخدم وسوق، محفوظة في PostgreSQL. الرجوع للسوق السابق يستعيد سلتها.
- Checkout يرفض خلط الأسواق أو السوق غير النشط ويعيد التحقق من العرض والمخزون والبائع.
- طلبات المستخدم القديمة تبقى متاحة له كطرف فيها حتى إن غيّر سوق التصفح؛ ليست بيانات عامة لسوق آخر.
- Seed: KW=1000/10³ KWD، JO=1000/10³ JOD، SA=100/10² SAR. **أسعار JO وSA إعدادات تطوير للاختبار، لا اعتماد تجاري.**
- سجل ISO العالمي يضم 249 دولة/سوقًا وبيانات 165 عملة؛ إنشاء الدولة أو وجود عملتها لا يعني أن السوق مفتوح.
- الأسواق الجديدة تبدأ `COMING_SOON` وبلا سعر. التسجيل لا يعتمد على جاهزية السوق: يستخدم سوق دولة الحساب إذا كان متاحًا، وإلا يفضّل `DEFAULT_MARKET` إن كان متاحًا، مع إبقاء التسجيل ممكنًا عند عدم وجود سوق مفتوح.
- تبديل سوق التصفح يقبل فقط `ACTIVE` أو `LIMITED` مع سعر حالي موجب؛ الخادم يفرض الشرط نفسه على عمليات النشر والطلب.
- إدارة السوق محصورة بدور `ADMIN`: الحالة والسياسات وطرق التنفيذ وأهلية البائع، مع نسخ أسعار فورية أو مجدولة وسجل تدقيق. العملة والسعر يختاران لكل سوق ولا توجد أسعار صرف تلقائية.

## E. MARKETPLACE

- حافظت على العروض وتعديلها، والكمية المحدودة وغير المحدودة، والسلة والطلبات والمحادثات والتسليم والنزاع والمستحقات.
- مسارات الذاكرة القديمة استُبدلت بمسار PostgreSQL واحد. بيانات `dinar-data.ts` متبقية كfixtures للتطوير/الاختبارات، ولا تخدم المستخدمين في runtime.
- Checkout داخل transaction، مع قفل صفوف المخزون بترتيب ثابت. جميع العناصر تُراجع قبل الحفظ، ثم يُنشأ طلب لكل بائع.
- إعادة المحاولة بمفتاح المستخدم نفسه والمدخلات نفسها تعيد الاستجابة المحفوظة ولا تنشئ طلبًا آخر؛ استعمال المفتاح لمدخلات مختلفة يرجع 409. يشمل ذلك إنشاء الطلب المباشر وCheckout السلة.
- LIMITED يحجز الكمية لمدة 30 دقيقة؛ عامل دوري يفحص الطلبات كل دقيقة ويحوّل الحجوزات المنتهية إلى CANCELLED ويحرر الكمية ويرسل رسالة نظام. محاولة قبول متأخرة ترجع 409. الإلغاء قبل القبول يحرر الكمية، وتأكيد المشتري يخصمها مرة واحدة. UNLIMITED لا يستهلك مخزونًا محدودًا.
- الأسعار والإجماليات والرسوم تأتي من الخادم. عمولة 10% تخص البائع، ولا تضاف كرسوم على المشتري.
- تعليمات التسليم تُتحقق عند الخادم (حتى 1000 حرف)، وتدخل في بصمة الطلب وتُحفظ ضمن الطلب فقط.
- Snapshot يشمل السوق والعملة وscale وسعر الوحدة والكمية والإجمالي والعمولة وصافي البائع، مع snapshots لكل عنصر.
- الطلبات والمحادثات محمية بعضوية الطرفين؛ قبول الطلب وإثبات التسليم للبائع، وتأكيد الاستلام/النزاع للمشتري.
- رسائل نظام محفوظة للإنشاء والقبول والتسليم والتأكيد والإلغاء والنزاع.
- فصلت المدينة والمنطقة العامة في إنشاء وتعديل العرض، وتتحقق API من طول ونوع المدينة. الدولة تأتي من سوق العرض.
- صفحة Checkout تعرض التنفيذ والتنسيق الخاص ومراجعة وضع الاختبار، دون وسائل دفع مزعومة. تعليمات التسليم الخاصة تحفظ داخل الطلب ولا تظهر في العرض العام.
- Seed منفصلة ومحروسة بعلم development، تتضمن أسواقًا وبائعين ومخزونًا محدودًا وغير محدود وطلبات بحالات مختلفة ومستحقًا ونزاعًا، ويمكن إعادة تشغيلها دون تكرار IDs الخاصة بها.

## G. SECURITY

- الهوية من session، لا من buyerId/sellerId/userId المرسلة.
- لا تعديل عرض الغير ولا قراءة/تعديل طلب أو محادثة الغير. لا endpoint لتعديل المستحقات من العميل.
- Drizzle parameterized queries، وZod في مسارات العمل، وقيود PostgreSQL.
- SameSite + رفض Origin المخالف وSec-Fetch-Site=cross-site، واشتراط JSON لطلبات الكتابة؛ أزيل CORS المفتوح.
- إخفاء stack traces عن العميل، وحد JSON 128KB، وno-store على API، وإخفاء X-Powered-By وnosniff.
- Rate limit للتسجيل والدخول: 20 محاولة لكل IP خلال 15 دقيقة، داخل عملية الخادم. مقارنة hash حتى عند عدم وجود المستخدم.
- لا unsafe HTML في الواجهات الجديدة، وروابط صور العروض الجديدة/المعدلة مقيدة بـHTTPS أو مسار محلي.

حدود أمنية قبل التشغيل العام:

- Rate limit ليس موزعًا ولا مخزنًا دائمًا؛ يلزم shared store وسياسة إضافية لكل هوية ومراقبة محاولات الإساءة.
- لا password recovery أو إدارة أجهزة وجلسات متعددة للمستخدم أو MFA.
- يلزم ضبط APP_ORIGIN وHTTPS وسياسة reverse proxy والنسخ الاحتياطي وأسرار البيئة، واختبار حمل ومراجعة أمن مستقلة.
- مفاتيح Checkout وعامل انتهاء الحجز يعملان ضمن خادم التطبيق وقاعدة التطوير؛ لا يوفّران تسوية دفع ولا يعالجان حالات Provider خارجية. لا تعد هذه نسخة إطلاق عام.
- لا خدمة حسم نزاعات أو صلاحيات فريق دعم/إدارة متكاملة، ولا فحص ملفات أو تخزين ملفات إنتاجي.

## التشغيل والتحقق محليًا

تحتاج DATABASE_URL لقاعدة تطوير. يسمح فحص CSRF بـ APP_ORIGIN عند ضبطه، وبنطاقات Replit runtime، أو بأصل reverse proxy الموثوق عبر X-Forwarded-Host/Proto، ثم يرجع إلى أصل الاتصال المباشر. لا تستخدم أوامر seed أو اختبارات التكامل على قاعدة Production.

```bash
pnpm --filter @workspace/db run migrate
pnpm --filter @workspace/db run check
BDINAR_SEED=development BDINAR_SEED_PASSWORD='<development-password-12-plus>' pnpm --filter @workspace/api-server run seed:development
pnpm --filter @workspace/api-server test
NODE_ENV=test LOG_LEVEL=error pnpm --filter @workspace/api-server run test:api
PORT=4173 BASE_PATH=/ pnpm run build
LOG_LEVEL=error pnpm --filter @workspace/api-server exec node test/run.mjs ui-server
# في طرفية أخرى:
pnpm --filter @workspace/dinar exec node test/visual.mjs
pnpm --filter @workspace/dinar exec node test/flows.mjs
```

اختبارات المتصفح الحالية تتوقع كلمة مرور seed التطوير المستخدمة في هذه الجلسة (`Development-only-2026!`) وأرقام fixtures `50000000` للمشتري و`50000005` للبائع الرقمي. هذه حسابات تطوير فقط، وليست حسابات إنتاج. يمكن ضبط CHROMIUM_PATH إذا اختلف مسار Chromium عن بيئة العمل الحالية. سكربت ui-server مخصص للتحقق المحلي وليس طريقة نشر.
