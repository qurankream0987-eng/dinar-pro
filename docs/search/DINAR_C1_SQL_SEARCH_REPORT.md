## 3. المعمارية قبل وبعد

**قبل:**
- كل بحث يقرأ السوق كله إلى الذاكرة (`SELECT * FROM offers JOIN users WHERE market_id = $1`).
- ثم يرشّح ويرتب في JavaScript.
- الترتيب العضوي دون `sort` = ترتيب كومة PostgreSQL، وهو غير محدد.

**بعد** (`DINAR_SEARCH_ENGINE=SQL`، الافتراضي):

1. **مرحلة SQL مرشِّحة هي مجموعة شاملة (superset) لما تقبله JavaScript.** كل شرط فيها ناتج عن قواعد JavaScript.

   | الشرط | التطابق مع JavaScript |
   |---|---|
   | السوق | تام |
   | `PUBLISHED`، أو البائع نفسه | تام |
   | `allowedIds` | تام |
   | التوفر في البحث الحواري | تام |
   | الفئة (بالمعرّف أو بالاسم القديم) | موسَّع |
   | السعر | موسَّع بهامش ±1 وحدة صغرى |
   | النص | موسَّع: أي إبرة لكل كلمة، في وثيقة بحث حديثة |

   البائع النشط، والفئات المقيدة، وقواعد السياسات، وبقية الفلاتر، وقواعد النص الدقيقة تبقى في JavaScript كما هي **حرفيًا** (الدالة `accepted` نفسها).
2. **القراءة على دفعات** بترتيب النتيجة النهائي. تُعاد الصياغة نفسها في JavaScript وهي مستقرة (stable).
   - **دون نص:** keyset على `(created_at, id)` أو مفاتيح السعر، ويمشي PostgreSQL على الفهرس ويتوقف عند حجم الدفعة.
   - **مع نص:** تُحسب مجموعة المرشحين مرة واحدة، وهي الوثائق المطابقة مع **كل** الإعلانات القديمة (stale)، بحد 20,000. ثم يرتب PostgreSQL معرّفاتها مرة واحدة، وتُقرأ الصفوف بهذا الترتيب.
   - **فوق الحد:** استعلام فرعي مضمَّن بلا خسارة.
3. **التوقف** حين يتوفر `limit` إعلانًا مقبولًا، **وقد تجاوز المسح كل إعلان مرعيّ ممكن**. فخانات الرعاية تحسب موضعه العضوي بالدقة نفسها.
4. **يُقرأ بالكامل ما هو محدود أصلًا:**
   - النتائج المخزنة، لأن لها ترتيبها الخاص.
   - ترتيب الخصائص، حفاظًا على تحويل `Number()` في JavaScript حرفيًا.
5. **وثائق البحث** (`offer_search_documents`):
   - النص نفسه الذي تبنيه دالة البحث (`searchableTextOf`)، لمراجعة (revision) محددة من الإعلان.
   - Trigger يرفع `search_revision` ويعلّم الإعلان قديمًا عند أي تغيير في `data`، وعند الإدراج، وعند تغيير فئة يسميها الإعلان (الاسم، أو الأسماء البديلة، أو الخصائص).
   - المحدِّث وحده يزيل العلامة، في **العبارة نفسها** التي تكتب الوثيقة، وبشرط أن المراجعة لم تتغير. فالتعديل المتزامن لا يترك نصًا قديمًا أبدًا (SF-05).
   - الإعلان القديم **دائمًا** مرشح، فالوثيقة الناقصة توسّع المرشحين ولا تخفي إعلانًا (SF-03).
6. **البائعون** لا يُربطون في الاستعلام، كي يمشي PostgreSQL على فهرس `offers` وحده. يُحمَّلون لكل دفعة بمعرّفاتهم.
7. **مسار القراءة لا يكتب.** التحديث يجري في خلفية الخادم كل 30 ثانية، بدفعات محدودة.

**الرجوع:** `DINAR_SEARCH_ENGINE=LEGACY` يحمّل السوق كاملًا كما قبل C1، بالقواعد والترتيب ذاتهما.

## 7. الترحيل `0041_c1_sql_search`

**إضافي فقط:**
- `CREATE EXTENSION IF NOT EXISTS pg_trgm`: امتداد trusted في PG13+، ينشئه مالك القاعدة. **يجب التحقق من الصلاحية في كل بيئة قبل النشر.**
- جدول `offer_search_documents`.
- عمودان بقيم افتراضية على `offers`. `ADD COLUMN … DEFAULT` في PG11+ لا يعيد كتابة الجدول. كل الصفوف القائمة تبدأ قديمة، وهذا صحيح.
- 8 فهارس:
  - على الوثائق: GIN trigram، وbtree للإصدار.
  - على `offers`: `(market, status, created_at, id)`، و`(market, status, price)`، وجزئي للقديمة، و`(market, data->>'categoryId')`، و`(market, data->>'category')`، و`(seller, created_at, id)`.
- triggerان.

**لا تغيير لأي قيمة قائمة، ولا حذف.**

**التسجيل:**
- `release-manifest.json` (sha256 `945ccc56…`).
- `REVIEWED_PENDING_MIGRATIONS`.
- اختبارا الرأس في `development-tls` (7/7) و`readiness` (15/15).

**القفل:**
- `CREATE INDEX` العادي يحجب الكتابة على `offers` أثناء البناء. حجم اليوم صغير، فهو ثوانٍ.
- لسوق كبير: يُبنى كل فهرس مسبقًا بـ`CREATE INDEX CONCURRENTLY` بالاسم نفسه. **ملاحظة:** الترحيل المولَّد لا يستخدم `IF NOT EXISTS`، فيلزم حينها تعديل مراجَع قبل الإصدار.

**ملء البيانات:** لا يلزم قبل التشغيل، فالبحث صحيح دونه. يبنيها `startSearchIndexMaintenance` في الخلفية، أو `refreshSearchDocuments` يدويًا.

**PostgreSQL 18:** **BLOCKED** (غير مثبت في البيئة). الترحيل لا يستخدم ميزة خاصة بإصدار. اختبار `lib/db test:release-migration` ما زال يحتاج PG18.

**الإلغاء اليدوي** (لا يلزم للرجوع الوظيفي):
```sql

DROP FUNCTION marketplace_categories_search_invalidate();

DROP FUNCTION offers_search_revision_guard();

  offers_market_category_id_idx, offers_market_category_label_idx, offers_seller_created_idx;
```

## 8. الأمان

- **لا حقل جديد يصل إلى العميل.** النص المفهرس في جدول منفصل لا يُقرأ إلا داخل استعلام المرشحين، فلا يمر بـ`select({ offer: offers })` في المسارات الأخرى.
- **النص المفهرس** هو النص الخام الذي كان البحث يطابقه أصلًا، دون الهاتف الخاص `contactPhone`. لا يُعاد أبدًا.
- **كل قيم SQL معاملات (parameters).** إبر `LIKE` مُهرّبة (`\`، و`%`، و`_`).
- **لا تجاوز لأي قاعدة أهلية:**
  - السوق، والحالة، والملكية، والبائع النشط، والفئات المقيدة، والسياسات، والتوفر، كلها مطبقة.
  - التشابه لا يتجاوز أي فلتر إلزامي: لا ترتيب بالتشابه أصلًا.

## 10. المخاطر المتبقية

1. **القاطع الوحيد للحداثة هو المحدِّث الخلفي.** بعد نشر الترحيل، كل الإعلانات قديمة حتى يمر المحدِّث. البحث صحيح لكنه أبطأ، ويقرأ كل القديمة. المحدِّث يبني ≈6k وثيقة/ثانية.
2. **تغيير `searchableTextOf`** يلزمه رفع `SEARCH_TEXT_VERSION`. حتى يُعاد البناء، لا تُستخدم الوثائق (أبطأ، لا أخطأ).
3. **النص الواسع جدًا** (أكثر من 20,000 مرشح) يعود إلى الاستعلام الفرعي المضمَّن.
4. **الإعلان المرعيّ المتأخر في الترتيب** يجبر المسح على الوصول إليه. هذه دقة مقصودة، ومحدود بعدد الحملات.
5. **الترتيب العضوي الجديد حتمي.** يختلف عن ترتيب الكومة القديم حيث لم يكن الترتيب محددًا.
6. **صلاحية `pg_trgm` وPG18** يجب التحقق منهما في كل بيئة نشر.
