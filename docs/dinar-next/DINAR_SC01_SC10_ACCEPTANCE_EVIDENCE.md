# DINAR — Claude 02: أدلة قبول SC01–SC10

**المرجع:** `docs/dinar-next/DINAR_TEN_END_TO_END_ACCEPTANCE_SCENARIOS.md`.
**الفرع:** `claude/02-sc-acceptance` (محلي، غير مرفوع). البداية `8117151`، و`SOURCE_SHA` للمصدر المختبَر = `398f32e` (الإصلاحات والاختبارات)، وهذا التقرير في الـcommit التالي له مباشرة.
**البيئة:** PostgreSQL 16.15 على loopback، وقاعدة جديدة لكل suite عبر `test/isolation/local-suite.sh`، وnet-guard، وstub للخطوط. لا Railway، ولا دفع حقيقي، ولا SMS.
**النموذج:** كل الاختبارات تستخدم gateway وهمي يرد `MODEL_FALLBACK` ويُعدّ استدعاءاته. **DeepSeek المباشر: NOT_AUTHORIZED** (لم يُستدعَ أي مزود مدفوع).

## 0. الخلاصة بصدق

- **لا يوجد سيناريو واحد PASS بمستوى REAL_E2E.** لم يُشغَّل أي سيناريو كاملًا من أول رسالة في متصفح حتى الإغلاق. نتائج المتصفح الموجودة (block-a، block-c، command-e-ui، g3-ui…) تغطي أسطحًا عامة، لا رحلات SC بعينها.
- ما أُثبت هنا مستوى **API_ONLY** عبر محرك المحادثة الحقيقي (HTTP → `/api/ai/conversations/:id/turns` → الطبقات الحتمية → قاعدة اختبار حقيقية)، مع إيصالات من قاعدة البيانات.
- **الطبقات المالية والصلاحيات قوية** (موروثة ومُعاد اختبارها في Claude 01): آخر قطعة، ثبات السعر المتفق عليه، الدفع الموقّع، التزام الاسترداد، رفض ادعاء الدفع.
- **الضعف كان في فهم العربية اليومية**: صيغ عادية كانت تسقط إلى النموذج أو تفتح السطح الخطأ أو لا تجد عروضًا موجودة. أُصلح منها 15 عيبًا عامًا (القسم 2). عدد الرسائل التي سقطت إلى النموذج في probe السيناريوهات: **16 → 9** من 40.
- **قدرات غير موجودة** (MISSING) تمنع إغلاق SC04/SC05/SC08/SC09 مهما تحسّنت المحادثة: خيارات المنتج (حار/عادي)، طلب عرض سعر منظم، المواعيد، تسليم الملفات الرقمية وإصداراتها، وتحويل العملات FX. هذه تحتاج تصميمًا وقرار مالك، لا إصلاح اختبار.
