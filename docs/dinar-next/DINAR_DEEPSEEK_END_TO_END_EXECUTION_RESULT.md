## 2. نتيجة DeepSeek الحية السابقة

لم تُرسل أي مكالمة استدلال حي إضافية في هذه المرحلة. التشغيل المصرح السابق استخدم النموذج `deepseek-flash` وأرسل **4 طلبات بالضبط من أصل 4**:

| الحالة | نتيجة التشغيل المحفوظة | رمز سجل الاستدعاء |
|---|---|---|
| إجابة عربية عامة | فشل التحقق من عقد DINAR | `MALFORMED` |
| نية بيع باللهجة الشامية | فشل التحقق من عقد DINAR | `UNAVAILABLE` |
| بحث ومقارنة | فشل التحقق من عقد DINAR | `MALFORMED` |
| متابعة مقارنة عرضين اصطناعيين | فشل التحقق من عقد DINAR | `UNAVAILABLE` |

النتيجة: **0/4 turns صالحة**. لم يحتفظ تشغيل benchmark بنصوص الاستجابات الفاشلة؛ لا يمكن إعادة استخدامها كـfixtures ولا الادعاء بمحتواها أو جودتها. اختبارات التوافق أدناه تستخدم fixtures اصطناعية موسومة بوضوح، وليست استجابات حية أو إعادة تشغيل لها.

| الاستخدام الحي المجمّع | القيمة |
|---|---:|
| طلبات الاستدلال | 4 |
| input tokens | 14,389 |
| منها cached input | 9,344 |
| output tokens | 2,000 |
| reasoning tokens | 1,376 |
| التكلفة التقديرية المجمّعة | **$0.003969** |
| حد الموافقة | **$0.03** |

لا تتوفر تفاصيل tokens أو التكلفة لكل حالة. التكلفة تقدير من الاستخدام المبلغ والأسعار المؤرخة، وليست فاتورة نهائية. احترم التشغيل سقف التكلفة والعدد، وانتهى التفويض ذي الأربع مكالمات؛ أي تشغيل حي جديد يحتاج موافقة جديدة.

## 3. التغييرات التي جرى التحقق منها

التنفيذ يعيد استخدام بوابة DINAR وطبقة المحادثة والأداة `dinarConversationTurn` وعقد Zod، ولا ينشئ chatbot أو runtime بديلين.

- يتيح اختيار `DEEPSEEK` للمحادثة مع حصر النموذج في `deepseek-flash` ونقل Chat Completions عبر `https://api.deepseek.com`.
- يفصل اعتماد benchmark (`DINAR_BENCH_DEEPSEEK_API_KEY`) عن اعتماد المحادثة (`DINAR_DEEPSEEK_API_KEY`)؛ لا يوجد fallback صامت بينهما أو إلى مزود آخر.
- يرسل طلب الأداة المنظم بوضع غير تفكيري (`reasoning_effort: none`) و`tool_choice: required`، مع حد `max_tokens` الخاص بـDeepSeek، ولا يمرر حقول DeepSeek إلى المزودين الآخرين.
- يحافظ على سجل الرسائل والسياق، ويتحقق من معاملات الأداة بعقد DINAR، ويعالج `finish_reason=length` كاستجابة غير مكتملة دون إعادة فوترة عبر retry.
- يصنف أخطاء المصادقة/الرصيد والحصة والانقطاع، ويستخدم usage المبلّغ عنه عند توفره. لا يرسل محتوى المزود أو بيانات الاعتماد إلى رسائل المستخدم.
- لا يؤدي فشل التحقق أو طلب الأداة غير المسموح إلى نشر إعلان أو إنشاء طلب أو تفاوض أو دفعة.

راجعت توثيق DeepSeek الرسمي لـ[Chat Completions](https://api-docs.deepseek.com/api/create-chat-completion)، و[Thinking Mode](https://api-docs.deepseek.com/guides/thinking_mode)، و[Tool Calls](https://api-docs.deepseek.com/guides/tool_calls). يوثق DeepSeek أن `reasoning_effort: none` يعطل التفكير، ويوثق استدعاء الأدوات في Chat Completions. شكل `tool_choice: required` في الاختبار الاصطناعي لا يثبت قبول مزود حي لهذا الإعداد؛ لم يُختبر طلب الإعداد الجديد على المزوّد بعد استهلاك حد الإنفاق.

## 4. اختبار المسار القانوني في DINAR

شغّلت الاختبار على PostgreSQL مؤقت مربوط بـloopback، بعد تطبيق migrations على قاعدة اختبار جديدة وإضافة أسواق ومستخدمين وسيارات اصطناعية فقط. استخدم الاختبار المسار الحقيقي `POST /api/ai/conversations/:id/turns`، حجز الاستخدام ودفتره، تنسيق المحادثة، عقد الأداة وSSE. استُبدل endpoint DeepSeek باستجابات اصطناعية موثقة الشكل، ورُفض أي مضيف خارجي آخر.

- طلب بلا سعر مسجل رُفض عند الحجز قبل أي طلب مزود.
- إجابة عربية اصطناعية مرت عبر route وظهرت في stream، مع تحقق من إعداد الطلب وسجل الاستخدام والتكلفة.
- مسار البيع الشامي أنشأ سطح مسودة البيع عبر قواعد DINAR؛ لم يستدعِ النموذج في هذه الحالة (`modelCalled=0`)، ولم ينشر عرضاً.
- بحث السيارات استخدم البحث القانوني للقراءة فقط وعرض **4 سيارات اختبار**؛ لم يستدعِ النموذج في هذه الحالة (`modelCalled=0`) ولم ينشئ عملية سوق.
- اختبار المتابعة أرسل تاريخ الرسائل السابق إلى adapter، وتحقق من بقاء سياق العرضين.
- اختبرت fixtures فشل الإخراج المبتور، والاستجابة غير الصالحة، وأخطاء 401 و429 و402 و503، بما فيها عدم إعادة المحاولة لحالة الإخراج المبتور، وإعادة محاولة 503 مرة واحدة ضمن اختبار محلي اصطناعي فقط.
- لم تُنشأ عروض منشورة أو طلبات أو مفاوضات أو نوايا دفع للمستخدم الاختباري. استُخدمت بيانات fixture فقط.

نتيجة `test:deepseek-chat` مع المتصفح: **10/10 ناجحة، صفر تخطٍ**. تضمّن المسار 11 طلباً اصطناعياً معترضاً إلى endpoint المحلي بعد إضافة حالة المتصفح؛ **صفر** مكالمات استدلال مدفوعة.

## 6. تفعيل DeepSeek مستقبلاً والتراجع

**لم يُفعّل DeepSeek الآن.** بعد الموافقة على التفعيل ومعالجة متطلبات قاعدة Preview فقط، يكون مسار الاختيار المقصود:

```text
DINAR_AI_PROVIDER=DEEPSEEK
DINAR_AI_MODEL=deepseek-flash
DINAR_AI_SPEND_REQUIRED=true
DINAR_DEEPSEEK_API_KEY=<سرّ مخصص لمحادثات التطبيق>
```

يجب إضافة سر محادثات التطبيق عبر إدارة الأسرار، منفصلاً عن `DINAR_BENCH_DEEPSEEK_API_KEY`. لا تنسخ مفتاح benchmark إلى الإعدادات أو الإنتاج. قبل تفعيل المحادثة يلزم أن تكون migrations المطلوبة مطبقة، وأن يوجد سعر صالح للنموذج وسياسة إنفاق مناسبة في بيئة التطبيق؛ لم أُنشئ هذه السجلات أو أطبق migrations.

للتراجع: أعد قيم `DINAR_AI_PROVIDER` و`DINAR_AI_MODEL` إلى القيم السابقة، أزل `DINAR_DEEPSEEK_API_KEY` من البيئة التي فُعّل فيها، ثم أعد تشغيل الخدمة. اترك مفتاح benchmark منفصلاً ولا تستخدمه كمسار تراجع.
