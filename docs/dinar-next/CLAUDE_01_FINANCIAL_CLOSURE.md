## 2. سياسة D3: التنفيذ والحالات المستخدمة

**مبدأ:** الدفع الموثّق لطلب ملغى أو منتهي الحجز **لا يُعامل كبيع أبداً، ولا يُتجاهل**. يتحول إلى التزام استرداد دائم واحد.

| العنصر | ما استُخدم |
|---|---|
| حالة الطلب | `CANCELLED` عبر الانتقال القائم `expireOrderReservation` (نُقل إلى `lib/order-expiry.ts`)، مع تحرير الحجز |
| حالة الـintent | `SIMULATION_BUYER_REFUND_DUE`، **حالة موجودة أصلاً** (يستخدمها مسار النزاعات). لا حالة جديدة |
| دليل الدفع | الحدث `CAPTURE_SUCCEEDED` يبقى، و`captured_amount_minor` لا يتغير، و`refunded_amount_minor` يبقى 0 |
| الالتزام | جدول جديد `payment_refund_obligations` (ترحيل 0040): صف واحد لكل intent، مرتبط بحدث الالتقاط، وسببه `RESERVATION_EXPIRED` أو `CAPTURE_AFTER_CANCELLATION`، وحالته `OPEN` ثم `RESOLVED` |
| منع التكرار | فهرس فريد على `payment_intent_id` وعلى `source_payment_event_id`، و`ON CONFLICT DO NOTHING`، وقفل الطلب ثم الـintent |
| منع المحو | Trigger يمنع DELETE وTRUNCATE وأي تعديل غير OPEN→RESOLVED. وRESOLVED يتطلب `REFUND_SUCCEEDED` لنفس الـintent. والإدراج يتطلب `CAPTURE_SUCCEEDED` لنفس الـintent والطلب |
| منع التسوية | الطلب الملغى لا يُقبل ولا يُسلَّم ولا يكتمل (409)، فلا ينشأ seller due ولا `SELLER_RELEASE_DUE` |
| عدم ادعاء الاسترداد | `SIMULATION_REFUNDED` لا يُكتب إلا عند `REFUND_SUCCEEDED` موقّع ومطابق للمبلغ والعملة وطلب الاسترداد. و`REFUND_FAILED` (حدث موقّع جديد) يترك الالتزام OPEN |
| مسار الإدارة | `GET /api/admin/payments/refund-obligations` (للإدارة فقط، قراءة). والاسترداد عبر `POST /api/admin/payments/intents/:id/refunds` القائم، وصار يقبل الالتزام غير المرتبط بنزاع |
| التسوية | `reconcilePayments` يتحقق أيضاً أن كل intent في REFUND_DUE له التزام OPEN، وأن كل التزام RESOLVED له intent مُسترد بالكامل |
| لا تنفيذ تلقائي | لا شيء ينفّذ استرداداً أو تحويلاً حقيقياً. المحول تجريبي فقط (`SIMULATION_ONLY`) |

### تغيير في D1 بسبب السياسة الجديدة

في Claude 00 كان الالتقاط المتأخر لطلب ملغى يُرفض بـ409 ولا يُسجَّل شيء. مع مزود حقيقي هذا يعني أن مالاً أُخذ دون سجل، وأن المزود يعيد المحاولة بلا نهاية. وهذا يخالف البند 1 من D3 ("لا تتجاهل الالتزام المالي"). صار الآن يُسجَّل كدليل ويتحول فوراً إلى التزام استرداد، ويُعاد 200 للمزود. **لا يصبح أبداً `SIMULATION_CAPTURED` لطلب ملغى**، وهذا هو جوهر D1.

## 6. الأمان والذكاء

- **حد الطلبات:** باقٍ. اختبارات جديدة للتداخل العميق (40,000 مصفوفة → 413؛ 20,000 كائن → 400؛ الخادم سليم)، وللجسم فوق 128KB (413)، وللطلبات المشروعة (ليست 413).
- **Zod:** ‏`pnpm audit` = 1 high ‏(`zod <4.6.6`، GHSA-mrhx-c7xc-m3w5). **OPEN**: الاستغلال محدود بحد العناصر، لكن الإصدار لم يُرقَّ.
- **حدود الذكاء** (`ai-authority-boundary`, 4/4):
  - النموذج يرى **3 أدوات قراءة فقط** (`getResource`, `openSurface`, `searchListings`)؛ و`addToCart` غير مكشوف له.
  - أي اسم أداة مالية يُرفض.
  - كل الإجراءات الـ19 تتطلب تأكيد المستخدم، ولا يوجد إجراء التقاط أو استرداد أو إلغاء أو تسوية أو عمولة أو تأكيد تسليم.
  - لا ملف في `src/ai` يستورد صلاحية مالية؛ نقطة الدفع الوحيدة intent تجريبي بتأكيد وتحقق ملكية.

## 7. مخاطر حرجة متبقية

1. **استرداد إداري لطلب نشط:** يمكن أن يكتمل الطلب بعده، فينشأ seller due (عمولة) على بيع مُسترد. قرار سياسة.
2. **لا حدث `PAYMENT_FAILED`:** الرفض يظهر في التسوية فقط.
3. **نزاع لصالح المشتري:** يبقى REFUND_DUE بلا مسار استرداد حتى ربط مزود حقيقي (سلوك Wave 4 القائم).
4. **PostgreSQL 18:** ترحيل 0040 لم يُختبر بمشغّل الإصدار على PG18. على PG16: يُطبَّق (41/41)، وخطة الإصدار تقبله، ولا SQL هدّام.
5. **Zod 4:** الترقية لم تُنفّذ.
6. **بيانات العينة:** تربط صوراً خارجية (Unsplash).
