# DINAR — Integration readiness and owner action matrix

**Audit date:** 2026-10-22  
**Repository:** `/home/runner/workspace`  
**Commit inspected:** `6b3bd80aec6182bff8377e5990492285bdb15e2a`  
**Scope:** Source/configuration inspection plus previously recorded development evidence. No secrets were read, no provider was called in this audit, and no managed database, production service, payment setting, or deployment was changed.

## Executive finding

DINAR has substantial internal marketplace, conversation, delivery, and simulated-commerce code. It is **not ready for a controlled pilot against the canonical development database**: the latest recorded Railway check found 28 of 37 migrations applied, with `0028`–`0036` pending, and the API readiness endpoint reported `503`/`migrations=pending`. The migration chain was rehearsed on a schema-only disposable PostgreSQL clone, but not applied to Railway and not rehearsed against a full data clone.

The app has provider interfaces and some development-only adapters; most customer-facing external services (real payments, SMS, push/email, mapping, and carrier tracking) are not connected. They are not all launch requirements: DINAR can support a limited local pilot with internal search/messaging, manual location/address details, and cash if its market policy allows it. Real billing, automated notifications, routing, and live GPS require separate decisions and implementations.

## Status legend

- **VERIFIED LIVE** — a real external service was exercised successfully in the relevant live environment.
- **VERIFIED DEVELOPMENT ONLY** — working evidence exists only in a development/test path.
- **IMPLEMENTED BUT UNCONFIGURED** — usable application adapter exists but lacks a required selection/configuration.
- **PARTIALLY IMPLEMENTED** — some code or interface exists, but an important capability or verification is absent.
- **MISSING** — no application implementation found.
- **NOT REQUIRED FOR INITIAL RELEASE** — deliberately optional if the stated internal/manual path is acceptable.
- **BLOCKED** — a concrete dependency or safety gate prevents readiness.

“Available secret name” does not prove a credential is valid, selected, or authorized. This audit did not inspect secret values or make external requests.

## Owner checklist

### ALREADY WORKING — NO ACTION REQUIRED

- DINAR’s internal password/session authentication, market-aware marketplace services, database-backed search, order/inquiry messaging, negotiation, simulated payment, and structured in-app order updates exist in source.
- Existing Replit AI Integration and App Storage environment-name sets are available in this workspace. Their values were not read; availability alone does not prove the provider or storage path is valid.
- No external search index, mapping provider, push provider, email service, phone carrier, live-payment provider, or courier network is currently selected.

### NEEDS API KEY / EXTERNAL ACCOUNT

- **No new key is currently required to proceed with the safe source-level audit or internal pilot design.**
- If production phone verification is a requirement, select an SMS vendor first, then create its account and implement the adapter. The app does not currently support a named vendor.
- If live subscription/payment collection is approved later, select a legally suitable processor for the launch market; do not add a key until the account, contract, sandbox flow, webhook verification, refund/dispute behavior, and accounting plan are agreed.
- If adding external maps, push/email, or carrier tracking, select the provider based on launch-country coverage and data-processing terms before requesting credentials.

### NEEDS CONFIGURATION ONLY

- **AI provider:** choose a server-side `DINAR_AI_PROVIDER` from the supported set and confirm its corresponding credential is valid. Groq is the code default when no provider is set, but the last documented smoke returned 401. Replit AI Integrations previously passed development smoke; this audit did not re-test it.
- **Storage:** confirm the configured Replit App Storage bucket and ACL-backed upload/download path with a small non-sensitive development fixture.
- **Recovery:** inspect Railway backup/PITR metadata and document the observed recovery window; do not make a service change without separate approval.

### NEEDS CODE OR ADAPTER IMPLEMENTATION

- Production SMS delivery, outbound email, browser push, live payment processing/webhooks, actual seller/courier payouts, provider-backed maps/geocoding/routes, continuous GPS tracking, and third-party shipment tracking.
- Dollar-based AI spend metering if the desired safety policy is a real currency ceiling; current usage controls are request/token-based.

### NEEDS OWNER COMMERCIAL DECISION

- Launch country/market and the legal model for handling subscription funds, buyer funds, seller settlements, courier compensation, refunds, and disputes.
- Whether paid plans/promotions will be sold for real money; whether processor fees and refunds are passed through or absorbed.
- Whether the initial pilot requires SMS, email/push, maps, carrier tracking, or remains in-app/manual.
- Which AI provider and maximum external spend are acceptable. Provider usage can be billed by Replit credits or directly by an external provider, depending on the selected integration.

### CAN BE POSTPONED

- External search indexing, external analytics, third-party moderation, geocoding/routes, continuous driver GPS, courier/carrier API, outbound push/email, and live payment/payout integration—provided the pilot scope explicitly accepts internal search, manual delivery, in-app updates, and no real-money collection.

## Five actions before pilot

1. **Resolve development readiness safely:** verify the recovery point, perform/record an isolated full-data clone rehearsal, then obtain explicit owner approval before applying `0028`–`0036` to the canonical development database.
2. **Restore and verify an AI path:** choose a provider and server-side configuration, check the provider’s authorization with an approved non-sensitive smoke, and set an out-of-band monetary usage limit.
3. **Verify storage end to end:** authenticated upload, owner-scoped read, public/private separation, and cleanup against test-created media only.
4. **Choose the pilot’s authentication and communication boundary:** either implement a production SMS adapter or explicitly change/approve the phone-verification launch policy; do not treat the development code-return path as SMS.
5. **Approve a pilot financial and delivery scope:** no real billing/payout until market/legal/provider decisions are complete; document whether in-app updates, manual address/location handoff, and cash are sufficient.

## Cost categories

- AI: token/request usage; Replit AI Integrations are billed to Replit credits at provider API rates, while own provider keys are billed by that provider.
- Railway: database compute and volume; backup/PITR storage and transfer may add usage costs. Service-specific backup state was not verified.
- App Storage: storage capacity, transfer, and object operations are usage-based.
- Future SMS/email/push/maps/carrier/payment services: typically per-message, per-request, per-transaction, or contracted fees; exact rates depend on provider and country and were not estimated here.
