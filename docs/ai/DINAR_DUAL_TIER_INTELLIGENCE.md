# DINAR — ذكاء بمستويين: LIGHT وHEAVY

**الفرع:** `claude/09-dual-tier`.

**الملفات:**
- `src/ai/model-tier.ts`.
- `src/ai/smart-turn.ts` (`draftWithClaimGuard`، و`executeModelFallback`).
- `src/ai/model-gateway.ts` (خانة HEAVY).

**الاختبار:** `test/model-tiers.test.ts` (10/10، بدائل مبرمجة، دون مزود حي).

## 1. البدائل الثلاثة

| | A: نموذج واحد بجهد تفكير متغير | B: نموذجان | C: هجين (DINAR الحتمي، ثم LIGHT، ثم HEAVY) |
|---|---|---|---|
| تكلفة الدور البسيط | منخفضة | منخفضة | **صفر** حين يحله DINAR، وإلا LIGHT |
| الطلب التحليلي | الجهد العالي يرفع الكمون والتكلفة للنموذج نفسه | نموذج أقوى | HEAVY فقط حين يُكسب |
| استدعاء إضافي للتوجيه | لا | غالبًا (مصنف) | **لا**، القرار حتمي |
| التعقيد التشغيلي | الأدنى | مزودان أو نموذجان | الأعلى قليلًا، ويعيد استخدام البوابة نفسها |
| يعمل دون مزود ثانٍ | نعم | لا | نعم (يرجع إلى A) |

**الاختيار: C،** مع A بديلًا تلقائيًا:
- DINAR الحتمي كان أصلًا الطبقة الأولى: البحث، والمراجعات، والقرارات، والخطط المقيدة لا تصل إلى النموذج.
- ما يصل إلى النموذج يذهب إلى LIGHT افتراضيًا.
- HEAVY حين تدل الإشارات الحتمية على حاجة.
- إن لم يُضبط نموذج HEAVY: النموذج نفسه بجهد `high` (`SAME_MODEL_HIGH_EFFORT`).

**لم يُدَّعَ أن أي نموذج أفضل:** المقارنة الحية `BLOCKED_OWNER_AUTHORIZATION`.

## 2. القواعد

1. **اختيار حتمي:** `selectModelTier(message)`، دون استدعاء نموذج. HEAVY لـ:
   - طلب طويل (`DINAR_AI_HEAVY_MIN_CHARS`، افتراضي 400).
   - تحليل أو شرح أو خطة أو مقارنة مفاهيم: «اشرح»، «حلل»، «ما الفرق»، «خطة»، «انصحني».
   - كتابة: «اكتبلي»، «صغ»، «وصف تسويقي».
   - ثلاثة أسئلة أو أكثر في رسالة واحدة.
2. **تصعيد واحد محدود:** إن أعاد LIGHT مخرجًا منظمًا غير صالح (`MALFORMED` أو `UNKNOWN_ACTION`) يُجرّب HEAVY مرة واحدة:
   - بالسياق نفسه، وداخل مهلة الدور نفسها.
   - **لا تصعيد** لتعطل (البديل يملكه)، ولا لمهلة (انقضت)، ولا لرفض حصة.
   - DT-04، وDT-05.
3. **القرارات لا تُصعَّد أبدًا** («نعم»، «أرسل»، «أوافق»): DT-09.
   - قبول الشروط لا يصل إلى أي مستوى.
   - «نعم» دون شيء معلّق كانت تصل إلى النموذج في السلوك القديم، وما زالت تصل إلى LIGHT فقط، ولا تنفذ شيئًا.
   - **عيب وُجد أثناء كتابة الاختبار وأُصلح:** القرار كان قابلًا للتصعيد بعد مخرج LIGHT غير صالح.
4. **سقف HEAVY لكل مستخدم:**
   - `DINAR_AI_HEAVY_TURNS_PER_WINDOW` (افتراضي 5، و0 = لا HEAVY) في نافذة أدوار النموذج نفسها (5 دقائق)، ضمن نطاق مستقل `conversation-model-heavy-actor`.
   - تجاوز السقف أو تعطل المحدِّد يُبقي الدور LIGHT (يفشل نحو الأرخص).
   - DT-06.
5. **البوابة نفسها:** كل مستوى يمر عبر `proposeThroughGateway`. التعطيل والقاطع والتكلفة تنطبق على كل منهما. HEAVY المعطل لا يُرسل ولا يُحسب (DT-08).
6. **التكلفة:**
   - حجز استخدام واحد للدور، وكل طلب مرسل (LIGHT ثم HEAVY) سجل تكلفة مستقل باسم نموذجه (DT-04: `providerCalls=2`).
   - المستخدم يُحمَّل إجابة واحدة فقط عند النجاح.
7. **التشغيل الافتراضي OFF:**
   - `DINAR_AI_TIERING` غير مضبوط = السلوك السابق تمامًا (DT-02).
   - خانة HEAVY في الجاهزية لا تظهر إلا عند ضبطها، فشكل `describeAIModelReadiness` لا يتغير (DT-10).

## 3. الإعداد

| المتغير | المعنى |
|---|---|
| `DINAR_AI_TIERING=on` | تفعيل المستويين |
| `DINAR_AI_HEAVY_PROVIDER` و`DINAR_AI_HEAVY_MODEL` | نموذج HEAVY. يشارك البديل الأساسي. المطابق للأساسي = لا نموذج ثانٍ |
| `DINAR_AI_HEAVY_TURNS_PER_WINDOW` | سقف HEAVY لكل مستخدم (0–20) |
| `DINAR_AI_HEAVY_MIN_CHARS` | طول الطلب الطويل (120–2000) |

## 4. المراقبة: التكلفة لكل مهمة ناجحة

**الحدث:** `dinar_ai_model_tier`. لا يحمل نص المستخدم. يحمل:
- `tier` و`reason` و`escalated` و`heavyKind`.
- `outcome` و`provider` و`model`.

**المقياس المستهدف:**

> التكلفة لكل مهمة ناجحة = Σ تكلفة كل الطلبات المرسلة (`ai_spend` لكل نداء، والفاشل منها أيضًا) ÷ عدد الأدوار التي انتهت بحجز `SETTLED`.

يُقسَّم حسب المستوى من حدث `dinar_ai_model_tier`.

**ما يحتاج إذنًا:**
- القياس الحي `BLOCKED`: مزود، ومفاتيح، وميزانية.
- إطار القياس جاهز: المجموعات C وH وG وS، و`MODEL_PROVIDER_BENCHMARK.md`.
- التوصية قبل التفعيل: تشغيل المجموعات بالوضعين (OFF وON) ومقارنة المقياس أعلاه، ومعدل التصعيد، والكمون p95.
